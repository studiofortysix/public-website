returns a successful HTTP response with the literal accepted:true. That endpoint

SPAM / RELIABILITY CONTROLS
- Server-side Turnstile success, exact contact action and exact origin/hostname.
- Valid, recent challenge timestamp; independent atomic token redemption before
  HubSpot forwarding. Storage failure blocks sending.
- Same-origin HTTPS requests only; no local hostnames in production configuration.
- Honeypot, bounded fields/JSON body, minimum elapsed time, no unexpected fields.
- Netlify rate limit: 5 requests per60 seconds per IP/domain.
- Official test secrets rejected in production. Missing configuration fails closed.
- Branch/unpublished Netlify deploy contexts cannot forward to HubSpot.
- Original live HubSpot form ID is always refused.
- Only the confirmed dedicated receiver and reviewed consent mapping are accepted.
- No automatic retry. Uncertain delivery locks repeat submission and offers email.
- Success is shown only after an explicit server acceptance response.

Scope: these checks protect the website's endpoint. HubSpot's unauthenticated
Forms API can also receive direct requests when its form identifiers are known;
those requests do not pass through this handler. A form ID is not a credential.
Do not claim that Turnstile protects every possible route into HubSpot. Check
HubSpot's own spam handling and monitor the dedicated form after activation.

TOKEN REPLAY CHECK
The real widget/secret pair successfully validated a fresh local token with the
expected contact action and exact local hostname. The local check contacted
Cloudflare only; it had no HubSpot receiver. Unexpectedly, a second redemption
also returned success, including when each request used a distinct idempotency
key and no-store headers. Cloudflare's documentation specifies single-use tokens;
the observed replay response did not meet that expectation.
The function therefore has its own atomic duplicate check using Netlify Blobs:
store studio46-enquiry-redemptions-v1, region us-east-2, onlyIfNew=true. Only a
SHA-256 token fingerprint and fixed marker are stored, with no email, IP address,
raw token, secret or enquiry text. Markers persist across deployments. No store
was created or written during this review; provisioning is automatic on use.
Concurrent, repeated and failed-storage cases are covered by offline tests.
Actual deployed-store operation remains part of activation verification.
The official @netlify/blobs SDK is pinned to11.1.6; Node22 is specified for the
build and package runtime. Its conditional request and duplicate-result handling
were checked with the actual SDK and a mocked HTTP transport. No real store write.
